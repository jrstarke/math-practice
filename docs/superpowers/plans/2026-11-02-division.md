# Division Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add division as a fourth operation that mirrors multiplication level for level, stays one level behind it,
teaches sharing with a "to share" pile, and switch every operation to a practise-what's-behind mix with a 3-problem
welcome after each unlock.

**Architecture:** A new `OpModule` (`src/core/operations/division.ts`) beside multiplication; `PictureState` gains an
optional `pile` that `pictureView` draws above the groups. Progress moves to v6 (`division` ladder + `welcome`
countdown). The learning-path file (`src/core/path.ts`) owns the unlock rule, the new cap rule and the new weights;
`adaptive.ts` stays operation-agnostic and just takes a `maxLevel`.

**Tech Stack:** Vanilla TypeScript, Vite PWA, Vitest (+ jsdom for UI tests), Playwright layout script.

**Spec:** `docs/superpowers/specs/2026-11-01-division-design.md`

## Global Constraints

- No new runtime dependencies; picture stays DOM + CSS.
- `MAX_LEVEL = 9`, `MAX_ANSWER = 4`.
- Every division problem divides evenly; divisor ≥ 1.
- No hint step (only Pass's final step) may reveal the answer in text, tally or picture; test this on the step model.
- Existing addition / subtraction / multiplication problem, hint and level tests pass unchanged (mix tests may change).
- Older saves are read once and never written; current key becomes `math-practice-progress-v6`.
- Commands need `PATH="$HOME/.asdf/shims:$PATH"`. Tests: `npx vitest run`; types: `npx tsc --noEmit`.
- `sed -i` fails on the /workspace mount; edit files with the Edit tool or node.
- Never push; the user deploys from the host.

## Review Focus

1. A save reloaded mid-welcome (or a hand-edited one whose welcome names a locked or unknown op): the welcome
   resumes, or the save is rejected as invalid, never a crash. → Task 1 storage tests, Task 3 welcome tests.
2. Multiplication slipping below division: division keeps its level, is still served at it, never above the cap.
   → Task 3 cap tests.
3. Rolling back to an older build: the v5 key must stay untouched after a v6 save. → Task 1.
4. Level 8 piles after a hundreds trade (345 ÷ 5 → 34 rods) and 10-group pictures on an iPhone SE Safari tab: must
   fit, not clip or overlap. → Task 5.
5. 0 ÷ n and ÷ 1 bubble text must not contain the answer digit. → Task 2.

### Task 2: Sharing hints and the pile

**Files:**
- Modify: `src/core/operations/types.ts` (`PictureState.pile?: PicturePart[]`), `src/core/operations/division.ts`,
  `src/core/operations/division.test.ts`

**Interfaces:**
- Consumes: Task 1's module.
- Produces: `solve(p): Step[]` for division. Every picture has `totalGroups = b`, `groupsShown = b`,
  `groupsOutlined = 0`, `groupSize = 0` (unused for division), `parts` = what each group holds so far (labels
  `'hundreds' | 'tens' | 'ones'` on L7/L8 and for answer-10 facts; any other label, e.g. `'each'`, = unit squares),
  `pile` = blocks still to share (same label rules). Multiplication never sets `pile`.

Step sequences (copy may be polished; structure may not):
- **Facts L1–6** with quotient q ≥ 2: (1) `Share N into d equal groups. d groups of what make N?` with empty groups
  and the full pile; (2) deal q − 1 rounds: `Deal one to each group at a time. How many in each group when it's all
  shared?`, tally `d, 2d, …, (q−1)d`, pile holds d. **q = 1, or answer 10** (40 ÷ 4, 90 ÷ 9: the pile is rods, one
  per group): step (1) only. **0 ÷ n:** one step, words only: `Share nothing into four groups. How many in each?`.
  **÷ 1:** one step: `Put them all in one group. How many are in it?`. Levels 4–5 use this default dealing (the spec
  allowed the simplification).
- **L9:** (1) naming as above; (2) `Give each group 5: d groups of 5 = 5d. R left to share.` (groups 5 each, pile R);
  (3) `Share the R into d groups. How many in each group altogether?` (same picture, tally adds a line).
- **L7/L8**, from the highest place: (1) naming, pile = dividend as flats/rods/squares; then for each place except
  ones, with `avail` = digit + 10 × carried: if `avail ≥ d`, a share step (`Share the tens: 2 tens in each group,
  1 ten left over.`) followed, if anything is left, by a trade step (`Trade the leftover ten for 10 ones. Now there
  are 12 ones.`); if `0 < avail < d`, one combined step (`Can't share 3 hundreds into 5 groups. Trade them for
  30 tens: 34 tens.`); if `avail = 0`, nothing. The last hint is always the ones: `Share 12 ones into 3 groups.
  How many in each group altogether?`, ones still in the pile.
- **Pass** (last step, `passOnly: true`): groups full, pile empty, keeps the last hint's tally.

- [ ] **Step 1: Write failing tests:**
  - for 1,000 seeded problems per level: last step `passOnly`, others not; every non-Pass step's pile is non-empty
    except 0 ÷ n; in every non-Pass step each group's block value (`count` × 100/10/1 by label) is `< q`, except
    0 ÷ n; no non-Pass text or tally line matches `new RegExp(\`(=|is) ${q}\\b\`)`; Pass's groups each total q;
  - every picture: `groupsShown === b`, `groupsOutlined === 0`;
  - sequences: `72 ÷ 3` → 4 hints + Pass with the texts above in order; `69 ÷ 3` → 3 hints (no trade); `345 ÷ 5` →
    the hint after naming starts "Can't share 3 hundreds"; `412 ÷ 4` has a tens "Can't share" step; `12 ÷ 6` → 2
    hints, step 2 tally `6`; `40 ÷ 4` → 1 hint, pile `[{ label: 'tens', count: 4 }]`; `42 ÷ 6` → 3 hints, step 2
    pile 12 squares;
  - 0 ÷ 4 and 9 ÷ 1 hint texts contain no digits (`/\d/` doesn't match).

### Task 3: Learning path — cap, weights, welcome

**Files:**
- Modify: `src/core/path.ts`, `src/core/adaptive.ts`, `src/core/session.ts`, `src/core/path.test.ts`,
  `src/core/session.test.ts` (and `adaptive`'s tests wherever they live)

**Interfaces:**
- Consumes: Task 1's `Progress` (with `welcome`).
- Produces:
  - `CAP_RULES: Partial<Record<OpKey, { by: OpKey; behind: number }>> = { division: { by: 'multiplication', behind: 1 } }`.
  - `maxLevelFor(p: Progress, key: OpKey): number`: `MAX_LEVEL` without a rule; with one,
    `by.level === MAX_LEVEL ? MAX_LEVEL : max(MIN_LEVEL, by.level − behind)`.
  - `update(s, score, maxLevel = MAX_LEVEL)`: a +1 change that would exceed `maxLevel` becomes 0 (calibration too);
    −1 unaffected; a level already above `maxLevel` stays.
  - `pickLevel(s, rng, maxLevel = MAX_LEVEL)`: the +1 pick falls back to current when it would exceed `maxLevel`.
  - `opWeight(p: Progress, key: OpKey): number` with `BEHIND_STEP = 0.25`, `MAX_WEIGHT = 2`, `BOOST_FROM_LEVEL = 3`:
    level 9 → `REVIEW_SHARE`; level < 3 → 1; else `min(2, 1 + 0.25 × gap)`, `gap = max(0, ref − level)`, where
    `ref` = highest level < 9 among unlocked ops (0 if none), and for a capped op `min(ref, maxLevelFor(p, key))`.
  - `WELCOME_PROBLEMS = 3`. `applyUnlocks` sets `welcome = { op: <last unlocked>, left: 3 }`. `pickOp` returns the
    welcome op while `welcome.left > 0` and it's unlocked; otherwise picks by `opWeight`.
  - `recordResult` decrements `welcome.left` (to `null` at 0) when `opKey(problem.op)` is the welcome op, before the
    off-level early return and before `applyUnlocks` can set a new welcome. `nextProblem` / `recordResult` pass
    `maxLevelFor(p, key)` to `pickLevel` / `update`.

  - `update` at level 4 with `maxLevel 4` and a perfect window → change 0, level 4; same during calibration; a miss
